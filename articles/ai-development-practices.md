自分が普段 AI をどう使い分けているか、開発時に何を意識しているかを整理してみる。

# 契約している AI サービス

現在、主に以下の 3 つを使い分けている。

- **Claude** ── コーディング用途がメイン
- **ChatGPT** ── 日常の雑談・質問・壁打ち
- **Gemini** ── 会社で利用可能。予定管理やニッチな用途

それぞれ課金して使っており、用途に応じて切り替えている。

# サービスごとの使い分け

## ChatGPT ── 日常の相棒

日常的にちょこちょこ話しかけたり質問を投げたりしている。たまにディープリサーチで調べ物をすることもある。

一番気に入っているのはインタラクティブな音声チャット。思考が詰まったときや頭が整理できないとき、ChatGPT と壁打ちに付き合ってもらうことが多い。過去の会話を結構覚えていてくれるので、文脈を踏まえた返答が返ってくるのが地味に便利で面白い。

## Gemini ── 予定管理と画像処理

稀に話を投げる程度だが、刺さる場面がある。

- 予定の追加をしたいとき、ざっくり予定が書いてある画像や連絡のスクリーンショットを Gemini に投げて、カレンダーに予定を入れてもらう
- ナノバナナを使いたいときに投げる

Google のエコシステムとの連携が強いので、カレンダー操作系は Gemini が一番手っ取り早い。

## Claude ── もっぱら開発

コーディングはほぼ全て Claude に任せている。基本的に開発は Claude Code で全部やる。

Claude Code の WebView もよく使っていて、出先でちょっとコードを書くこともある。環境を立ち上げてやるほどでもないこと、サクッと終わりそうなタスクは Web の方に投げてしまい、そっちでタスクを完結させることもある。

# Claude Code の開発プラクティス

## 常に最新版を使う

ローカルの Claude Code を使うとき、環境を立ち上げたらまず mise で Claude Code をアップグレードする。常に最新版を使うのが癖になっている。最近は自動アップデートが入ることもあるが、念のため毎回手動でも確認している。

## マーケットプレイスのスキルを定期チェック

定期的に Claude Code 公式のマーケットプレイスを覗きに行って、新しいスキルやプラグインが配布されていないかをチェックする。基本的に公式のマーケットプレイスしか見ていないが、結構有用なスキルが登録されている。認証が不要なものであれば、公式のスキルはとりあえず全部入れるようにしている。

## 設定はプロジェクトスコープに置く

Claude Code の設定は基本的にプロジェクトスコープにして `.claude` の下に置くようにしている。どういうスキルを使っているか、どういうプラグインを使っているか、共通して書くルールはどうか、全てをリポジトリに含めて同期できる状態にしてある。

## docstring に背景情報を残す指示

コーディング時に基本の指示として入れているのが、**背景情報を docstring に詳細に残す**ということ。なぜこれをやるのか、なぜこの実装にしたのかという背景情報を、コードの中にしっかり書き残しておくよう指示している。

## テンプレートで横断的に設定を同期

プロジェクトに限らず横断してやらせたいこと ── たとえば Claude Code の設定、スキル、プラグイン、共通ルール ── はテンプレートで管理して同期している。

ワークスペースではいつも DevContainer を使って開発しているので、DevContainer の設定や mise の設定などの情報は全部テンプレートとして管理している。

- テンプレートに更新が入った場合 → コマンドを入力してテンプレート側にプッシュ
- テンプレートに変更があった場合 → プルしてテンプレートから持ってくる

この双方向同期の仕組みで、プロジェクト間・リポジトリ間で設定を統一できている。

## Jujutsu でバージョン管理

Claude Code でパラレルに開発をするようになってから、Jujutsu（jj）を使い始めた。正直まだ完全に理解しきれていない部分もあるが、Git を使っていたときよりも雑にコミットを打つようになった。コンフリクトや問題が起きても「戻せるでしょう」という気持ちで、今どのブランチにいるかをそこまで意識せずに指示を投げている。必要に応じてリベースやコンフリクト解決の指示を出す形で進めている。

## サブモジュールでマルチリポ管理

会社のプロジェクトでは特に顕著だが、管理用のルートリポジトリを作って、関連するリポジトリをその下にサブモジュールで入れている。こうすることで、全てのコンテキストをルートで起動した Claude Code から読みに行ける状態で作業ができる。

ルート側に必要に応じてフックを入れて、特定のタイミングでテストを実行するなどの制御も行っている。

## MCP と CLI でサブツールを活用

MCP や CLI をサブツール的に使って開発を進めている。

### SQL 作成の工夫

会社で SQL を使ってプロダクトの DB からデータを引っ張りたい・調査したいというケースでは、全部 AI にクエリを書かせられる環境を作っている。

Redash を使っているので、以下のような仕組みにしている。

1. Redash のスキーマ情報をローカルにインポート
2. ローカルに PostgreSQL の DB を立てる（データは空だがスキーマは Redash と同一）
3. AI が書いたクエリをまずローカルの空 DB に投げて、構文が通ることを確認
4. 問題なければ Redash に持っていって実行

顧客情報が入っている本番 DB に直接書きに行くのはセキュリティリスクが高すぎるので、あくまでスキーマ情報だけをローカルに置くという方針。これにより「Redash にクエリを持っていったけどエラーで動かない」という手戻りを防げる。

### Chrome DevTools MCP

Chrome DevTools MCP も使っている。DevContainer の中に Playwright と Chrome を入れて、動作確認が必要なときは DevTools を使って Claude に検証してもらう。ホストの Chrome ではなく、DevContainer 内で完結する形にしている。

これは AI に動作確認ができる状態を作っておくと勝手にイテレーションを回してくれるという話そのもの。作業後の動作確認を Claude が自律的に行える環境を整えておくと、開発のサイクルが速くなる。

# 音声入力で指示を出す

AI に指示を出すとき、**できるだけ手で書かない**ようにしている。ほぼ全ての指示を音声入力で出す。

なぜか。口で喋っている方が情報量が多いと感じているから。

人に話すのと同じテンションで喋ると、自然と「これをやってください」だけでなく、「なぜならこういう背景があって、こういうことをやりたいからこの指示を出している」という背景情報も含めて伝えることができる。手で書くと端的でスッキリした文章になりがちで、その分いろんな情報が抜け落ちるし、なるべく文字を書かないでおこうという意識が働いてしまう。

音声入力なら、口が勝手に動いてコンテキスト情報まで自然に含められる。これが習慣化すると、AI に渡すコンテキストの質が上がり、アウトプットの精度も上がる。

# まとめ

自分が AI を使う上で意識していることを振り返ると、大きく以下に集約される。

- **用途に応じてサービスを使い分ける** ── 全部を一つのサービスに寄せるのではなく、得意領域で切り替える
- **AI が自律的に動ける環境を作る** ── 動作確認できる状態、スキーマ情報へのアクセス、テスト実行環境など
- **設定やルールを横断的に同期する** ── テンプレートを使ったプロジェクト間の設定統一
- **背景情報をケチらない** ── docstring に残す、音声入力で自然に情報量を増やす
- **常に最新のツールを使う** ── アップデートの確認とスキルの導入を怠らない

AI をうまく使うコツは、結局のところ「AI が仕事をしやすい環境を整えてあげること」と「質の高いコンテキストを渡すこと」に尽きると思っている。
